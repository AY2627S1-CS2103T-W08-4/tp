## Findings

### A02 — Standard JAR lacks ARM64 Mac natives (deployment risk; provisional Medium)

- Fix location: `gradle/universal-mac.gradle:12`, applied from `build.gradle`.
- Published v1.5 `addressbook.jar` exits on plain ARM64 Java 25.0.3 with
  incompatible x86_64 JavaFX native-library errors. The course's Mac installation
  guide recommends Java with bundled FX, which is a working workaround; this is
  not a claim that every supported Mac setup fails.
- The course and DG nevertheless target one artifact for both Mac architectures.
  The old separate ARM JAR is not a single-artifact solution.
- Implemented build-only universal Mach-O wrapping for the seven existing JavaFX
  17.0.7 Mac native binaries. No new dependency version, native compiler, runtime
  extraction mechanism or command/model behavior is introduced.
- Apple's `lipo -verify_arch x86_64 arm64` accepts all seven outputs. Both slices
  are byte-identical to the original Intel/ARM release binaries. Windows `.dll`
  and Linux `.so` entries are byte-identical to the published standard JAR.
- The same final JAR passed real-window command/selection/attendance/update,
  save/reload and clean-exit probes under plain ARM64 Java 25.0.3 and plain Intel
  Java 25.0.3 through Rosetta. Rosetta is not physical Intel hardware verification.
- The normal `java -jar` entry point also reached the v1.6 main UI from a different
  working directory. Its process was stopped by the audit after startup; normal
  typed exit was tested in the packaged-window harness and the automated suite.
- `shadowJar` now produces one 12,898,862-byte artifact. The legacy ARM build task
  aliases it without producing another JAR. CI is configured to build the JAR on
  all three platforms; that revised remote workflow has not been run yet.
- Updated v1.6 packaging instructions, DevOps explanation, runtime version and
  window title. Existing documentation PR #118 needs integration reconciliation.
- Full final macOS FX-JDK check/coverage/build passed **460 tests**, zero
  failures/errors/skips. Both Checkstyle tasks and repository scripts pass.

### A04 — Minimum window height exceeds the smallest scaled viewport (Medium)

- Fix location: `src/main/resources/view/MainWindow.fxml:15`.
- The original FXML forces a 600px minimum window height. A settled real-window
  test requesting 853x480 (the logical size of 1280x720 at 150%) measured 600px.
  The packaged JavaFX 17 window reproduced the same minimum.
- Lowered the minimum to 400px. The new regression checks the settled outer
  height, a usable scrolling roster, visible command input and selected details
  within the scene. It failed before the resource change and passes afterward,
  together with the existing roster and class-view UI tests and Checkstyle.
- This is logical-viewport simulation on macOS, not a claim of actual Windows
  150% scaling verification. Physical screen/OS-scale combinations still need a
  release-owner smoke test.

### A03 — Packaged app writes outside its home folder (Medium / constraint)

- Fix locations: `commons/core/ApplicationPaths.java:18`, `MainApp.java:40` and
  `commons/core/LogsCenter.java:26`, under `src/main/java/seedu/address/`.
- A baseline packaged startup/exit probe launched from a different directory
  created its data, preferences and logs there, rather than beside its JAR.
- Fixed with a shared application-directory resolver. Unpackaged development
  retains its existing working-directory behavior. No existing external dataset
  is silently imported; the UG explains keeping the data folder beside the JAR.
- A real miniature JAR test covers spaces and `%t` in its directory name, proving
  URI decoding and literal FileHandler path handling. Startup, logger and path
  tests plus both Checkstyle tasks passed on macOS / Java 25.0.3 FX.
- Actual rebuilt full-JAR startup and restart from a separate empty folder both
  loaded/saved six students beside the JAR. The launch folder remained empty.
- Public course constraint, not a new team feature decision. No remote issue/PR
  created; review this intentional location-contract change before integration.

### A01 — Logging failure prevents application startup (provisional Medium)

- Fix location: `src/main/java/seedu/address/commons/core/LogsCenter.java:93`.
- Confirmed in a fresh Java process against baseline packaged main classes.
- Start in a disposable folder containing a directory named `addressbook.log.0`.
  This forces FileHandler creation to fail; an unwritable log location has the
  same error path.
- Expected: log a warning to the already-installed console handler and continue.
- Actual: `ExceptionInInitializerError`, caused by NullPointerException at
  `LogsCenter.setBaseLogger`, because the static `logger` field is assigned only
  after that method returns. Main initializes logging before opening the app.
- Minimal fix candidate: report through the initialized `baseLogger`. Test in
  separate processes because the failed class initialization poisons that JVM.
- No corresponding open issue was present when issues were read. Local finding;
  no remote issue/PR created.
- Implemented the minimal console fallback and removed the initialization-only
  logger. The fresh-process regression fails before the fix. After the fix, both
  logging tests, the four independent integration tests and Checkstyle pass.

## Final evidence and limitations

- Full checks: macOS ARM64 / Zulu Java 25.0.3 FX. Packaged runtime probes:
  plain Zulu Java 25.0.3 ARM64 and Intel x64 through Rosetta, same JAR hash.
- All three requested logical viewports (1920x1080, 1536x864, 853x480) were
  inspected after actual resize pulses on both JVM architectures. Small-window
  command input, scrolling roster, selected-detail scrolling and status footer
  remain reachable. This simulates viewport sizes, not actual OS DPI settings.
- A 250-student real-window test exercises recycled cells after scrolling to the
  last student, deleting an earlier row, filtering and marking the last class
  member, then returning to the full roster. Visible row numbers, names, emails,
  selected details and persisted attendance match the intended students. This is
  a bounded correctness probe, not a capacity/performance guarantee.
- Read-only/no-op operations did not write to a deliberately obstructed target.
  Failed mutating commands retained original bytes and model/filter state before
  successful retries. Existing real-window tests also check selection and input.
- All 55 concrete guide command examples, including parameterless command
  forms, were represented by 35 valid and 20 invalid executions, using fresh
  appropriate student or legacy fixtures. Placeholders and prose fragments are
  not executable commands; contextual multi-command behavior has separate tests.
- Published UG/DG/home page render; their in-page links resolve. Source sequence
  diagrams for update, mark, delete, find and startup and the student/legacy model
  were compared with code. Current edited docs have not been locally rendered:
  Jekyll fails because locked Bundler 2.5.11 is unavailable with system Ruby.
  Dependencies/lockfiles were not changed to force that check through.
- Fresh Windows/Linux runs of the new commits are unavailable without publishing
  or a suitable connected machine. Baseline remote passes and preserved native
  bytes are supporting evidence, not substitutes. Revised CI is ready locally.
- Multi-monitor removal warning: added real-window regression passes on current
  Mac JavaFX; no restoration change made. Windows/Linux behavior remains a manual
  check. Existing UG recovery instructions remain precautionary.
- No unsupported-atomic-filesystem device, physical Intel Mac, exhaustive hardware
  matrix, screen reader, concurrent-instance synchronization, unbounded stress or
  exhaustive input-space test was available/performed. Single-user offline scope
  does not establish a concurrent-writer guarantee. No real student data used.
- Pure code-quality opportunities such as inherited equals/hashCode asymmetries
  on command/index helper types were not turned into user-facing bug claims:
  their hash-container use was not found in current command paths. Avoid broad
  cleanup during the freeze. No tests/assertions were weakened or excluded.
- Final conventional diff is **44 added/deleted functional lines** including the
  FXML edit (34 Java additions, 8 Java removals, one FXML addition/removal). This
  is a conservative patch-size estimate, not final RepoSense attribution. It is
  below the initial 150-line minimum; recheck the official report before merge.
  Even including all added/deleted build/CI glue, the conventional estimate is
  142 lines, so the patch does not depend on excluding that glue to stay below 150.
- Final JaCoCo: 1,815/1,930 lines, 744/812 branches. Coverage is not a correctness
  claim; child-JVM logging/path regressions are not instrumented by the parent's
  JaCoCo agent. Baseline and final counts must not be compared as identical scopes.
